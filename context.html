Context and budget

A model can only read so much at once. That limit is its context window, and in a long roleplay the chat outgrows it long before you are done. Ashyo treats the window as a budget: it works out what every part of the prompt costs, keeps what matters most, and drops the oldest history when something has to go. This page explains the arithmetic, what is never dropped, how costs are estimated, and the two tools that let you see the prompt itself.

The budget

Three numbers decide how much of a prompt fits:

  • Context size. The model's window in tokens, from the chat's connection. It is usually learned from the provider, or you set it by hand; see Context size.
  • Generation reserve. Room kept free for the reply. It is the Max length or Max tokens sampler, see Samplers.
  • Estimator margin. A fixed 500 tokens of slack when the provider cannot count tokens exactly, so an estimate that runs slightly short does not overflow the model. With KoboldCPP and llama.cpp, which count exactly, the margin is 0.

The effective budget is the context size minus the reserve minus the margin, and the whole prompt must fit inside it. Lore has a budget of its own carved out of the same window, a percentage you set on the Lore tab, see Lore books. All of this appears as the Budget block in a reply's itemization: a bar showing how full the window was, then rows for Context size, Generation reserve, Estimator margin, Effective budget, Lore budget as "used of allowed" and Remaining, with "Over budget" in red when the prompt did not fit. Where a provider reports the real count of the prompt it read, the bar shows that measured figure rather than the estimate.

A send needs a context size. If none is known, Ashyo asks the provider for one first, and when that fails too the send is refused: "The provider's context window is unknown and could not be retrieved. Test the connection or set a context size." The one place a prompt is planned without a size is the inspector preview, and then nothing is evicted.

Tip

The status bar's right end always shows the current chat's usage as a small bar and "used / size (pct%)", green under half, red past 80%. It is the quickest way to notice a chat is about to start losing history. See The screen.

What gets dropped, and in what order

Some of the prompt is fixed and some is negotiable. Ashyo never evicts the system prompt, your persona, the character's description, personality and scenario, post-history instructions, lore outlets, the instruct template's filler message or a /sysgen prompt. The message you just sent is pinned too, and so is the reply being continued when you use Continue. Everything else can go:

  1. Example messages first. The character's example dialogue and any lore placed around it are the first to leave, before a single chat message is touched.
  2. Then chat history, oldest first. History is filled from the newest message backward. The first message that does not fit marks the cut: it and everything older is dropped, even if some small older message would have squeezed in. The model therefore always sees an unbroken run of the most recent turns.
  3. Lore last. Lore entries placed before or after the character, or at a depth in the history, outlive the history. They are dropped only when the fixed content and the pinned messages could not fit otherwise, lowest priority first.

When the provider can count tokens, Ashyo measures the whole planned prompt after estimating it and evicts more if the measurement disagrees, in up to a few passes. If the server still answers that the prompt was too long, Ashyo trims again with one extra margin and resends once. A prompt that cannot be made to fit, because even the fixed parts and the pinned message exceed the budget, fails with "The prompt does not fit the context budget: X tokens against the Y that fit. The system prompt and the last user message are never evicted, so raise the context size, lower the generation reserve, or shorten them."

You can see where the model's view of history began in two places. The transcript draws a centered "last prompt starts here" divider at that point when Show context marker is on, and the itemization lists everything evicted as runs: the first and last message dropped, how many, and how many tokens they held, with examples as one run and lore entries one by one. A lore outlet whose host text was itself evicted is listed as unused.

Token estimation

Every item in the prompt gets a size from the best source available, and the itemization tells you which one was used:

  • Backend token count. The provider tokenized the text itself. KoboldCPP and llama.cpp count each item, the whole rendered prompt with its special tokens, and the reply. Hosted providers report counts for the prompt as a whole after the fact.
  • Byte classes. Ashyo's own estimate from the kind of characters in the text: plain letters and spaces cost about a quarter of a token each, digits more, and multi-byte characters more still. It is close enough, and the estimator margin covers the difference.
  • Fixed template overhead. The per-message wrapping a Chat Completions request carries, taken as 4 tokens per message after messages have been merged and post-processed. With Text Completions the overhead is the story string scaffolding, the instruct sequences and the generation prefix, counted as text; in single-user mode the "Name: " labels count too.
  • Unknown. No source could size the item.

Counts are remembered per message while its text is unchanged, so a long chat is not recounted every turn. A count that fails, for example because a local server is down, silently falls back to the next source. Reply sizes come from the provider's usage figures, with the completion count excluding reasoning. When a reply records what the provider actually read, the itemization treats that as the measured total and shares it out across categories in proportion to their estimates.

The prompt inspector

When you want to see exactly what is about to leave, turn on the inspector with /inspector. It is a per-chat switch, and the command's description in the completion list reads "Inspector: on" or "Inspector: off" so you always know its state. While it is on, every send, swipe and continue first opens a Prompt inspector box showing the exact prompt after a short loading line: the rendered text for Text Completions, or the message list as JSON for Chat Completions. Scroll it with the usual keys, then press Enter to send it unchanged or Esc to cancel. What you previewed is what goes out, with one exception: a prompt planned while the context size was unknown is planned again at send time.

Prompt itemization

After the fact, any reply can show you the prompt it came from. Mark the reply in the transcript, open its actions menu with Tab and choose Itemization (offered for a single reply once the chat has finished loading). A Prompt itemization box opens with three tabs you switch with Tab, Shift+Tab or a click: Overview, Breakdown and Prompt as sent. Tabs that have nothing to show are dimmed.

The header tells you how trustworthy the view is. "Recorded" means the prompt was frozen when the reply was generated and read back from disk. "This session only" means it is held in memory and no record was written, so it is lost when Ashyo restarts. "Not recorded" means there is nothing to show, and the box says so: "Nothing to show for this message." A reply that was moved between branches gets a note, since its turn numbers refer to the path it was generated on.

Overview

The facts of the request: Request (send, swipe, continue or sysgen), Provider, Protocol, Model, Instruct template, Served by (the host that actually answered, where the provider reports one) and Served model when it differs from the one you asked for, Persona, Character and Generated. Then the token breakdown by category, System prompt, Injections and Chat history, each with its count and share, and under each the kinds it holds (description, personality, examples, lore by position, scenario, persona, and so on). Then the Budget block described above, followed by anything evicted and finally "Skipped lore entries (N)" with a reason per entry. All counts use thousands separators.

Breakdown

Every item in the prompt as one row: a ▶ or ▼ fold marker, a header such as "Turn 3 · Ada" or "Lore at depth 4 (system) · Castle", a muted preview of the text and its token estimate on the right, or "—" when unknown. Move with ↑ and ↓ and press Enter to unfold a row. An unfolded item shows where it came from (Context Template, Chat history, Lore book "name" or Character card), its eviction policy (Never or On overflow), what triggered it if it is lore, any outlet it fed, and its full text. Turn numbers follow the branch the reply was made for, and an outlet feeding a row's prefix is credited to the first item of that row.

Prompt as sent

The prompt as one wrapped text, exactly as the provider received it. Drag with the mouse or press Ctrl+A to select, and Ctrl+C to copy. Text that is no longer available reads "[content unavailable]", or "[content unavailable: message deleted]" and "[content unavailable: superseded by a later edit]" when you have since deleted or edited the message it came from.

Reading the lore labels

The itemization is the place to find out why a lore entry did or did not make it into the prompt. An entry that fired carries a trigger label: "Always included" for placed content that is not lore, "Constant" for a constant entry, "Decorator @@activate", "Matched "key"" with where the key was found (in the scenario, in a recursion pass, in a widened scan), "Matched "key" and "secondary"", "and every secondary key", "and no secondary key" or "without "secondary"" for the secondary-key rules, and "Sticky, N more messages". Group outcomes follow as "won group "G" by most keys", "as prioritized", "by weighted pick", "as kept by group "H"" or "as sticky", and finally "rolled X of Y%" for a probability roll.

An entry that did not fire is listed under "Skipped lore entries" with one of these reasons: "Over the lore budget (N tokens)", "Delayed until recursion" or "Delayed until recursion level N", "Failed its roll: X of Y%", "Lost group "G" to "W"", "On cooldown, N more messages", "Delayed until the chat holds N messages", "Outlet "name" is not used in the prompt", "No outlet name" and "The example messages are not in the prompt". What each of those mechanisms is, and the settings behind them, is explained under Lore books.

Prompt records

Every reply can keep a record of the prompt that produced it: the request type, the provider, protocol and model, the settings in force, the measured and provider-reported counts, the budget, the lore report, every evicted run and every item with its estimate and provenance. The record is stored in the chat file beside the reply, which is what makes "Recorded" itemizations survive a restart. Branch copies inherit the record of the message they were copied from, and the record of a reply also fixes where the model's view of history began for the Show context marker divider.

Records are compact because unchanged message text is read back from the chat itself rather than stored twice; only rewritten text and non-message items keep their own copy. Records written by a future version of Ashyo in a different format are ignored rather than converted. Timed lore effects such as sticky and cooldown are carried forward from the nearest earlier reply that still has a prompt in memory or a record, following copies back to their originals, so they keep working after you switch branches.
