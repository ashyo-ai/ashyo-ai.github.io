Sessions

A session is an append-only log of events. Nothing in it is ever rewritten, which is what makes branching, resuming, and switching models safe.

On disk

WhatPath
Session log~/.local/share/ashyo/sessions/<uuid>.jsonl
Index~/.local/share/ashyo/sessions/index.db
Scratch directory~/.local/share/ashyo/sessions/<uuid>.scratch/

The log is one JSON object per line, one event each, in the order they happened. The index is a SQLite database with full-text search over the logs; it also records, for every line, where it sits in its file and what its row in the session tree reads, which is what lets a session be opened without reading its log. It is reconciled against the logs when Ashyo opens the store, so the logs are the truth: delete index.db and the next start rebuilds it from them. The scratch directory holds the plan document, per-run markers, and the whole of any tool result too large to put in a request. Session ids are UUIDs; the store rejects anything else before composing a path.

Events

Every event has an id and a parent id. The event types are:

TypeMeaning
sessionThe root: creation time, directory, surface. On a session made by /clone or /fork it also carries an origin — which kind of copy it was, and the id of the session it was copied from. See Where a copy came from.
messageA user or model message, or a tool call and its result, stored as the provider produced it. A model message also carries the token usage its provider reported for it, which is what the session box adds up, and a timing beside it — how long the provider took to its first output and to the finished answer, measured here rather than reported by anyone. That is what the model picker's speed columns are read from, across every session you have. A message recorded before Ashyo kept either carries neither.
customA harness record on the path, such as a tool call's lifecycle. A tool call's record keeps the call as the model made it — intent and all, since arguments are stored as received — the call that ran, the decision, and toolVersion: the version of the tool the call was made against. A call naming a tool that is not registered carries no toolVersion, because there is no contract to name.
session_titleA rename.
model_change, thinking_level_change, mode_change/model, /thinking, and /plan. Every model_change in the store is also what the model picker lists as recently chosen, so that group is a reading of the logs and is rebuilt with the index.
permission_decisionAn interactive allow or deny, with the intended, approved, and executed call.
hook_eventWhat each hook said.
subagent_start, subagent_resultA child's beginning and its compact result.
advisorWhat the advisor said, and when.
approved_planThe plan you approved, with its hash.
todo_changeThe whole task list as it stands after one change the todo tool made — never a patch of the change before it. The latest one on the path is the list in force there.
context_clear/clear: the model's conversation starts below this point.
compactionOne run of the compaction ladder: which of the three methods ran and what it took out of the request — the results a clean removed, the results and blocks a shake replaced with the ids they can be read back by, or a summary with the point it covers through. Nothing is deleted.
context_trim, context_compactionThe two markers earlier versions of Ashyo wrote. Nothing writes them any more and both are still read, so a session that has one folds exactly as it always did — see the older markers.
node_labelA label you wrote on one node in the session tree. It annotates that node and is on no branch: no path runs through it, so no transcript and no request ever carries it.
session_exitHow the run ended: normal, interrupt, or crash.

Branching

Because every event names its parent, a session is a tree, and what you see in the transcript is one path from the root to a leaf. Open the tree with /tree or two Esc presses, pick an earlier node, and send a message: the new event's parent is that node, so you now have two leaves. The old branch is untouched. Switch between them any time; both are there after a restart.

The model, the reasoning effort, plan mode, and the task list are all events on the path, so switching branches restores exactly the state that branch had. Resuming does the same.

/clear is a node on the path too. It clears the model's context without ending the conversation: every request after it is built from the part of the path below the marker, so the model starts with nothing said, while the turns above it stay in the session untouched. The tree shows it as a clear node under the last message; the transcript empties and says nothing, live and on a later resume. Select the node above it and send, and you have a new branch with the whole conversation back; the cleared branch is untouched beside it. Everything the path carries — the title, the model, the reasoning effort, plan mode, the task list, and the session's permission rules — is read across the marker, so a cleared conversation runs exactly as it was configured.

Messages typed while a turn is running are queued on the branch you typed them into and sent together as the next turn. They stay with that branch across a switch.

A subagent belongs to a branch too. Switching to a branch that does not hold the request that started it ends it, and its result is recorded on the branch that asked for it rather than on the one you moved to; one whose request is on the branch you switch to keeps working. /clear ends none of them. See the branch a child belongs to.

Compaction

Every model has a window, and a long conversation fills it. Without something to do about it the only way on is /clear, which forgets the whole thread. Ashyo instead takes things out of the request — never out of the session — and does it in three steps of rising cost, stopping as soon as the conversation fits again.

One threshold

compaction.threshold is a percent of the active model's window; 80% unless you say otherwise. What is measured is the input token count the provider reported for the model's last answer. After a compaction Ashyo estimates the new figure from the bytes it removed, and keeps that estimate until the next answer reports a real one.

The ladder runs wherever the conversation crosses the threshold, not only where a turn happens to begin:

  • as a turn ends, when its last answer was at or over;
  • between the requests of one turn, after a batch of tool results is recorded and before the next request is built — so a long turn of commands and file reads compacts as it goes instead of dying half-way;
  • after a request the provider refused for the window, or an answer that stopped short: the ladder runs and the request is retried, which needs no window at all, because the refusal is its own measurement;
  • at session start, so a conversation you left near the limit is compacted before the model reads it again;
  • while the session sits untouched for compaction.idleAfter, if you set one.

One compaction runs at a time and a turn cannot start while one is running. A message you send during one is queued behind it and goes out with the compacted context.

Clean

The first step costs nothing and loses nothing. It runs within compaction.cleanMargin points below the threshold — ten by default, so from 70% — and takes out what the conversation has already overtaken and what told the model nothing in the first place.

  • A file read is stale once a later write or edit touches that file, whatever lines either covered, because the content and the line numbers have both moved; and once a later read covers the same lines. It is sent as [superseded by a newer read of this file].
  • A web fetch is stale once the same URL is fetched again; a command's output is stale once the identical command runs again in the same directory.
  • A useless result is removed outright, its call left standing with an empty answer: a glob, grep, or web search that matched nothing, a command that printed nothing, a read of an empty file, and any call that failed. The tool itself says so when it answers, so this is a mark Ashyo reads rather than a guess about the text.

Clean ignores how recent a result is — stale is stale — and runs once as the conversation enters that band, not again while it stays there. Leaving the band and coming back cleans afresh, and so does /clear or a branch switch.

Shake

The second step runs on crossing the threshold. It replaces recoverable content with a short line and keeps every byte of it in the log:

[compacted — read session://3f2a91c4 to recover]

A file read names the file as well, so the model can read it as it is now instead of what it said an hour ago:

[compacted — read src/internal/tui/overlay.go again, or session://3f2a91c4 for what it was]

What counts as a unit: a tool result's whole text — shell output, file reads, glob and grep results, web fetches and searches, images — and, inside something you or the model wrote, a fenced block or a top-level XML block of at least four hundred tokens. The block scanner is deliberately narrow: a fence opens on three backticks or three tildes at the start of a line, an element opens on a line holding one lowercase tag at column zero and closes on its closing tag at column zero, a nested tag belongs to the outermost, and an unterminated fence, an unclosed tag, indented markup, and mixed-case markup are all invisible to it. Tool calls and reasoning are never scanned. A block missed costs tokens; a block invented costs the model its own words.

The most recent compaction.protectTokens of the conversation are left alone — sixteen thousand by default — measured over what the model is actually sent. That is the work in hand, whatever turn it is in. A useless result ignores that protection and is taken wherever it sits.

A shake is all or nothing: Ashyo adds up what it would save, counting sixteen tokens for each line it leaves behind, and if the total is below compaction.minSavings it replaces nothing. Every compaction invalidates the provider's cached prefix from the first replaced byte down, and a saving too small to pay for that is no saving. There is no minimum size for one unit, though: a fifty-token listing outside the protected region takes a line like a fifty-kilobyte read.

After a request the window refused, the shake runs as a rescue with the protected region and the minimum saving both at zero — the request did not fit, so everything recoverable goes.

Getting compacted content back

read session://3f2a91c4 returns exactly what the line stands for: a tool result whole as it was recorded, an image as the image, a block as its own text, with offset and limit paging it as they page a file. Nothing was copied anywhere to make that work — the id is in the session log beside the content it names — so it answers after a restart, in a clone, and in a fork, and no file can be deleted out from under it.

Summarize

The last step is the only one that loses anything and the only one that costs a model request, which is why the two cheaper ones run first and why a summary they made unnecessary is never written. Everything before the most recent protectTokens is summarized by the model the conversation is running on — because that is the model that will read it back — into one message. The boundary is moved up to the nearest point between a tool result and the next request, so a call is never separated from its result. When nothing lies before the protected region the whole conversation is summarized; when the only thing before it is an earlier summary, nothing is written.

The summary is written from the conversation as the model is sent it, placeholders and all, and from then on every request opens with it:

Earlier work in this conversation was compacted into the summary below.
Continue from it; do not redo what it says is done.

<compacted>
...
</compacted>

If the summarizing request itself does not fit, the turn fails with a line naming the window: the conversation is larger than anything that model can read.

What you see

A muted line in the transcript where each compaction happened, naming the method and nothing else:

── compacted: shake ──────────────────────────────

No saving is shown, because without a tokenizer it is an estimate; the status line's context bar shows what actually happened at the next answer. The line is drawn the moment it happens — mid-turn included — and again when you reopen the session.

A summary's line stands where the turns it covers were, with the transcript above it taken off the screen the way /clear takes turns off. Focus the transcript with Tab and press Enter on it to open it on the summary the model reads; press again to close it. Earlier markers are inside the collapsed part. The session tree is untouched: every turn is still a row, and Enter on a row above a summary gives you a branch with the whole conversation back.

Nothing is deleted

The fold is in the request and nowhere else. Each run appends one compaction event saying what it removed; the turns themselves stay exactly where they were, the transcript draws every result at its full length, the tree shows every node, and the log keeps every byte. Because it is a record on the path rather than a rule applied afresh at each request, resuming, cloning, and forking all build the same request from the same branch, and a branch taken from above a summary carries the whole conversation again. /clear cuts the ladder with everything else: below a clear the conversation starts uncompacted.

Print runs and subagents compact on the same threshold, because the ladder lives in the loop that makes model requests. The idle rule and the transcript marker are the interactive surface's alone, and the advisor's own context is never touched.

The window is read from the model catalog, which is what each provider publishes about its models. A model no catalog has heard of is measured against nothing and is never compacted on the threshold — Ashyo will not fold a conversation on a number it does not have — until you give it one with contextLength on the model's entry, which also overrides a published number that is wrong. Such a model still compacts after a refused request, where the refusal is the measurement. What a summarizing pass spends is counted in the session box's token rows like any other pass and adds nothing to the message counts, because nobody typed it and nothing answers it; a clean and a shake cost no request at all.

The older markers

Earlier versions of Ashyo folded the request two other ways: a context_trim that sent every tool result above it as its first 256 bytes and one line, and a context_compaction that replaced every turn up to a point with a handoff. Nothing writes either any more. Both are still read, so a session that has one goes on folding exactly as it did and there is nothing to migrate.

Cloning

/clone takes a copy of the whole conversation and carries on in it. Everything is copied: the log, the scratch directory with its plan document, and the session of every subagent the conversation ran, each under a new id of its own. The copy opens on the branch the original was on, under the same title, with the same model, reasoning effort, mode, session rules, and task list, and the pane shows exactly what it was showing a moment before — only the status line's session field changes, to the copy's id.

The original is never written to. It stays in the picker, resumable, with everything it had, and no session_exit is written to it: the surface lets it go rather than closing it. Two rows now share one title, the copy above the original, and the copy's row is badged (clone) so you can tell which is which — see Where a copy came from. /rename is how they part for good.

The two share nothing afterwards. Turns you take in the copy are recorded under the copy, turns you take in the original stay in the original, and deleting either leaves the other whole, its subagent records included.

Three things do not travel. A mutable subagent's worktree is git state rather than a session file, so it is not copied and stays with the conversation that made it, which is where you clean it up; the copy's own subagent_start and subagent_result events still name it. Memory is global, so nothing is copied there and the turns the original already consolidated are not consolidated again. Input history belongs to the project rather than the session, so a clone changes nothing about what the composer recalls.

/clone takes no argument, and is refused while a turn is running or while a subagent is still running, so no log is copied while something is writing to it. A clone that fails part-way leaves no new session behind and the conversation you were in still bound.

The advisor is the one writer that is waited out rather than refused, because it runs on its own after a turn ends and can still be working when the composer is free. A pass still at its model is cancelled and writes nothing to either session; a pass already recording finishes recording first. Either way the copy holds every line the original holds. Anything the advisor had already said and the model had not yet read travels with the copy and goes out with your next message there — including a blocker that would have started a turn of its own, which starts none: not in the original, which you have left, and not in the copy, which never asked for it.

Forking

/fork takes a copy of the branch you are on and carries on in it. Where /clone copies the whole conversation, a fork copies one path through it: everything from the start of the conversation down to the leaf you are on, the sessions of the subagents that branch ran, and the scratch directory with its plan document, each under a new id of its own. The copy opens on its leaf, and /tree in it shows that one path with no other branch.

What the other branches hold does not come along. A title, a model switch, a reasoning effort, plan mode, a /clear, a change to the task list, or a session rule set on a branch you were not on is not in the copy, and neither is a subagent only that branch ran — the fork carries exactly what its own path carried, which is what the transcript was showing you. Labels are the exception in your favour: a label naming a node on the forked path comes along wherever you wrote it, so the copy's tree shows the same rows named. A label naming a node on another branch does not.

The original is never written to. It stays in the picker with every branch it had, resumable, and no session_exit is written to it. Two rows share one title, the fork above the original, and the fork's row is badged (fork) — see Where a copy came from. /rename is how they part for good, and everything cloning says about worktrees, memory, input history, and deleting either side holds here too.

/fork takes no argument, and is refused while a turn is running or while a subagent is still running, so no log is copied while something is writing to it. A fork that fails part-way leaves no new session behind and the conversation you were in still bound. The advisor is waited out exactly as cloning describes, with one difference the narrower copy makes: advice recorded on a branch the fork does not take stays with the original, because the copy holds no line to show it against.

To fork from an earlier point, open the session tree, put the highlight on the turn to go back to, and press Ctrl-F: the copy is the conversation down to the end of that turn, so what was said after it is left with the original along with every other branch. To fork from a point inside a turn — one answer of several, or a call — open the turn with → first and highlight the row itself. Everything else is what /fork does — the same subagent sessions, the same labels, the same refusals — and the original keeps the branch it was on rather than moving to the turn you forked, which is the difference between forking a row and switching to it.

Where a copy came from

A copy keeps the title of the session it came from, so two rows in the picker read alike. What tells them apart is a field on the copy rather than a mark on its title: its session event carries an origin naming the kind of copy — clone or fork — and the id of the session it was copied from. Nothing else moves, so the status line, the transcript, and every request the model is sent read exactly as they did in the original, and no /rename is needed to strip a prefix off the title.

Two places show it. The session picker draws the kind after the title as (clone) or (fork), so the copy's row is the one that says what it is; the original's row says nothing. /session reads the whole of it, on an Origin row under the id: Origin: clone of 6f1c2a0e-….

Every session a copy writes carries one, the subagent records included, and each names its own source rather than the conversation at the top. A copy of a copy names the copy it came from, so a clone taken inside a fork reads clone and names that fork: follow the ids one at a time and you walk back to the conversation the chain started from. Deleting a source changes nothing about the copies of it — the id is a record of where they came from, not a link that has to resolve, so the badge still reads and the id names a session that is gone.

Sessions written before Ashyo kept this carry no origin and read as they always did: no badge on the row, no Origin row in the box.

Titles

A new session is titled from its first prompt, cut to 80 characters. /rename <title> renames it; the rename is an event, and the picker reflects it at once.

Finding a session

In the TUI, Ctrl-S shows sessions created in the current directory, and Tab widens to all. From the shell:

$ ashyo session list
$ ashyo session search 'sqlite wal'
$ ashyo session resume 6f1c2a0e-3b7d-4c1e-9a2f-0d8e5b4c7a11

Opening a session

Opening a session costs what is read out of it, not how long it has run. Ashyo builds the shape of the conversation — every event, its parent, and its place — from the index, and goes to the log only for the turns something is about to show you: the ones since the last /clear, and above that the settings the branch carries, such as the model, the reasoning effort, the mode, the session rules and the task list. A message from before a clear is still on the branch, still in the log, and still copied by /clone and /fork; it is simply not read until something asks for it. A session that has run for a year opens as quickly as one started this morning, and Ashyo holds the turns it has shown you rather than the whole history.

Before trusting the index Ashyo checks it against the file: the log's size, its modification time, and the hash of its last line. Anything that does not match — a log another program appended to, a log truncated, a log whose last line was edited — and the whole file is read back and indexed again, which is also what repairs an index that has fallen behind. Editing a log by hand in the middle, in a way that leaves its length and its timestamp exactly as they were, is the one change this check does not notice; nothing Ashyo itself does can produce it.

The first start after upgrading to a build that records this reads every log in the store once, to fill in what it did not record before. That start is as slow as every start used to be. Nothing is lost, nothing is asked, and every start after it is fast.

Resuming

ashyo session resume <id> opens the TUI on that session's current leaf. If the session cannot be opened, because it is missing, corrupt, or already open in another Ashyo, the surface starts with no session bound and the picker as the way out; press Ctrl-S.

One Ashyo per session

A running surface leaves a marker in the session's scratch directory. A second Ashyo refuses to open the same session while the marker is live. If a run dies without exiting, the next start finds the stale marker and writes a session_exit with reason crash, so the transcript says what happened instead of ending mid-sentence. Reopening that session also records any subagent the dead run left working as ended, so none of them is shown as running for good.

Export and delete

$ ashyo session export 6f1c2a0e-3b7d-4c1e-9a2f-0d8e5b4c7a11 > session.json
$ ashyo session delete 6f1c2a0e-3b7d-4c1e-9a2f-0d8e5b4c7a11

Export writes the session as JSON to stdout. Delete removes the log, its scratch directory, and its index rows.
