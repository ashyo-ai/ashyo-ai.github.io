Tools

Ashyo ships a fixed set of seventeen tools and no way to add more. Every call goes through the same policy and hook path, and the model is told when a result was cut short.

Tool definitions are sent to the provider in strict mode. A required argument that is missing or null comes back to the model as tool_error naming the argument, and the tool does not run.

What a call is for

Every tool takes one argument the table above does not list: intent, one line saying what the call is for, in the model's own words. It is required on every call, added to every definition in one place, and taken back off before the tool runs — so no tool's own arguments changed and no tool ever sees it.

It is shown wherever the call is. The transcript's tool line reads tool: shell — read the crash log. The session tree's row reads the same, and typing what a call was for finds that row — opening the turn it sits in — which is how you pick one shell call out of forty. A docked approval shows it above the arguments, so the reason for a call is read before the mechanics of it.

Rules ignore it unless you point one at it. A matcher on /command or /path decides exactly as it did before intents existed; a matcher on /intent matches what the model wrote — worth knowing is that the model writes it, so it is evidence about a call and not a control over one.

The intent is required by the schema, so a provider holding the roster to it never sends a call without one. A call that arrives without one anyway still runs, and every surface then draws it the way it drew calls before: the tool's name alone.

Tool versions

Each tool carries a version: a small integer, starting at 1, bumped whenever the tool's arguments or the shape of its output change. It is not a release number and nothing behaves differently because of it.

What it is for is the log. Every call recorded in a session carries the version it was made against, as toolVersion on the tool lifecycle record, so reading a session months later tells a call made under one contract from a call made under the next — which reading the arguments alone cannot.

Paths

A read whose path begins session:// is not a path at all: it names something the compaction ladder took out of the model's context, and it is answered from the session's own log — whole, or paged by offset and limit as a file is. Nothing is resolved against the filesystem for it, so no permission rule about files has anything to say about it, and an id this conversation never minted is a visible error the model can correct. See Getting compacted content back.

File tools resolve paths against the workspace root, your home directory, and the conversation's own scratch directory. A path outside all three is refused with path_outside_workspace. Named pipes, sockets, and devices are refused by read, edit, and grep, so a tool cannot be parked forever on a FIFO.

Ignored paths

glob and grep honor the workspace's .gitignore unless you set gitignore to false. A directory the file excludes is stepped over whole, so a search of the workspace does not walk into build output or a vendored dependency and come back with a compiled binary's bytes. A path you ask for by name is always searched, whatever the workspace ignores.

Anchoring an edit

edit applies its operations only when the hash they carry is the file's, so a model working from a stale view is refused instead of clobbering the file. The hash comes from the tools themselves. A read of a text file opens with it:

file_hash: 3c720cbfdb33922bb72de70f212e78a25a5b820974615ba239d69be22f1ac677
1:package main
2:
3:func main() {

and a successful edit ends with the file's new one, so a second edit to the same file costs no second read. The hash is of the whole file rather than of the window read out of it, so a paged read still anchors an edit, and it is the first line rather than the last because the output cap keeps the head of a result and spills the rest.

A file that moved underneath the model is refused with content_drift, and that refusal does not say what the file hashes to now: re-anchoring without looking at the file again is exactly what the anchor exists to prevent. The model reads the file and tries again.

Limits

Every limit that cuts a result short is announced to the model in the result itself, so a partial file never reads as the whole file.

The output cap

One cap covers every tool there is: no single result may put more than 64 KiB into a request. A longer result is written whole to tool-output/<call-id>.txt in the conversation's scratch directory, and what the model receives is one notice line followed by the first 64 KiB, cut at a character boundary:

tool_truncated: showing the first 65536 of 312904 bytes; the whole output is at ~/.local/share/ashyo/sessions/<uuid>.scratch/tool-output/call_31c9.txt

The notice comes first so that anything cutting the tail of a result later takes the cut bytes and leaves the sentence explaining them. The model reads the rest back with read, on the path the notice gives it. The file is copied by /clone and /fork along with the rest of the scratch directory, and is deleted with the session. A failed call over the cap is cut the same way and stays a failure. If the scratch directory cannot be written, the result is still cut and the notice says the rest was not kept.

The transcript shows the capped result, notice and all — it is what the model was handed. The per-tool limits below sit underneath the cap: each tool decides which of its bytes matter, and the cap decides how many of them reach the request.

shell

The command string is passed to bash -lc unchanged, in the session's working directory unless cwd is given, as your user, with your environment. There is no allow-list and no argument parsing; the rule engine sees the whole string at /command, which is what makes a regex rule meaningful. Output is the tail of stdout and stderr with the exit code. A timeout ends the command and says so.

Web tools

web_search queries DuckDuckGo's HTML endpoint and parses the results; a CAPTCHA page or a non-2xx response is a visible tool error, not an empty result. With webSearch.backend set to auto, the provider's own search is offered to the model when the provider supports one, and Ashyo falls back to the local tool if the provider rejects it. Set duckduckgo to always use the local tool. web_fetch reads a page as text and is the way to open a search result.

Task list

todo keeps a list of tasks the model works from: set replaces the list, add appends to it, update moves one task to pending, in_progress, completed, or blocked, clear empties it, and view reads it. Every call answers with the whole list, so the list you read in the transcript is the list the model has.

The list belongs to the conversation rather than to the running program. Each change is an event on the path, exactly as a model switch or /plan is, and the list in force is the latest change on the branch you are on. So going back to an earlier turn in the session tree shows the model the list as it was there — empty, if that branch never made one — and coming back shows the later list again. Resuming a session opens on the list it had, and /clone and /fork carry it into the copy. /clear does not empty it: it clears what the model has been told, not what the conversation is working on.

Nothing new appears in the transcript, because the tool's own reply already shows the list. The tree shows one todo row per change, so you can see where the list moved and go back to any of them.

A subagent has a list of its own, in its own session. It starts empty rather than inheriting the parent's, and nothing it writes there reaches the conversation that spawned it.
