Connections

Ashyo does not run a model itself. It talks to one: a server on your own machine, a hosted API, or a subscription. A connection is the handful of settings that say which service that is, how to reach it, who you are to it and which model to ask for. This page walks through setting one up and then explains each provider in turn.

How a connection is set up

Everything about a connection lives on the Connection tab of Settings (/settings). The tab shows only the rows the chosen provider actually uses, plus the few every provider shares, so it changes shape when you switch providers. From top to bottom you will find:

  • Preset. A saved connection to start from, listed as "name · provider · protocol", or None. It reads "No saved presets." until you save one. See Presets.
  • Provider and Protocol, under Route. Which service you are talking to (it reads "No provider selected" until you choose) and whether you talk to it with Chat Completions or Text Completions. The protocol list only offers what the provider supports.
  • Address, Port and Base URL, under Endpoint. Local servers take an address and a port (1–65535). The OpenAI-compatible provider takes a base URL instead, which must start with http or https and name a host. Hosted services show none of these.
  • Account and a credential row, under Authentication. Which of your saved accounts to use, then either an API key row or a Login row depending on the provider. Local servers skip this section. See Accounts and credentials.
  • Model. A searchable list of what the service offers. See Choosing a model.
  • Extra request fields. A JSON object merged into every request, for servers that take options Ashyo has no row for. Only llama.cpp and OpenAI-compatible servers show it.
  • Model providers, Model quantizations and Allow fallback providers, under Routing. OpenRouter only. See OpenRouter.
  • Context size and Auto-update on connect. How many tokens the model can read at once. See Context size.
  • Connection, under Test. Press Enter on it to try the connection. See Testing the connection.

With a chat open, the tab edits that chat's connection and the header counts your unsaved changes ("No unsaved changes." or "3 unsaved changes."). With no chat open it edits the defaults every new chat starts from. A row you changed away from its preset is marked with "∗ " and offers a Reset action. The whole mechanism is explained in Settings and presets.

Chat Completions and Text Completions

There are two ways to hand a model a conversation, and the protocol row picks which one Ashyo uses.

With Chat Completions, Ashyo sends a list of messages, each tagged as system, user or assistant, and the server wraps them in the model's own format. It is the simpler choice and the only one hosted services offer. How Ashyo arranges the list is described under Prompt building.

With Text Completions, Ashyo builds the entire prompt as one piece of text and the server continues it. You control the wrapping yourself through an instruct template, which is why this protocol has a far longer list of samplers and is the only one that can continue a reply mid-sentence. Both local servers speak it.

Tip

Samplers belong to a protocol, not a provider. Switching between Chat and Text Completions switches which sampler preset applies, and the Samplers tab only appears once a protocol is set.

KoboldCPP

The default provider. KoboldCPP serves one model at a time from your own machine, so the connection is just an Address and Port, defaulting to 127.0.0.1 and 5001, with no encryption. There is no model row: Ashyo asks the server what it has loaded and stamps that name on every reply.

KoboldCPP is also the provider Ashyo knows best. The server reports its true maximum context length, so context size fills itself in, and it counts tokens exactly, so prompt estimates carry no safety margin. Every text-completions sampler is sent under the name KoboldCPP expects, and stopping a reply tells the server to abort generation rather than just closing the connection.

llama.cpp

The llama.cpp server, reached by Address and Port with defaults of 127.0.0.1 and 8080. It speaks Text Completions through its OpenAI-style endpoint, so it shares most of its behavior with the OpenAI-compatible provider, including the sampler translation described under What gets sent.

The Model list shows a "Loaded model" entry above whatever the server lists. You can leave the row empty: the reply is then stamped with the first model the server names. The context size is read from the server's own settings, and tokens are counted exactly, so there is no estimate margin here either. Extra request fields let you pass server options Ashyo has no row for.

OpenAI-compatible

For any server that speaks the OpenAI API, from a local program to a hosted service. There is no default address: you give a Base URL such as http://127.0.0.1:1234/v1, and it must start with http or https and name a host. The provider offers both protocols, lists models from the server, and shows an Extra request fields row.

  • Model. Pick one from the server's list, or type any name; the list offers your text as "Use <text>". The model is only included in requests when you set one, since many local servers ignore it.
  • Extra request fields. A JSON object merged into every request last, so a key you set here overrides what Ashyo would have generated. Setting a key to null removes it from the request entirely.
  • API key. Many servers need none. If yours does, add an account and paste the key; it goes out as a bearer token.

Because a generic server cannot be asked how it tokenizes, Ashyo estimates prompt sizes itself and keeps a 500-token margin in reserve, see Token estimation. When the server reports that the prompt was too long, Ashyo trims and resends once. Error messages come from the server as it phrases them.

OpenRouter

A hosted gateway that routes one request to many underlying model hosts. It is Chat Completions only, always over an encrypted connection, and it is the one provider that insists on a key: a send without one fails with "API key is required." Create a key on the OpenRouter site, then save it under an account.

  • Model. OpenRouter's full catalog with display names and context lengths. Names are matched without regard to case, and a ":variant" suffix is dropped.
  • Model providers. Which hosts may serve the model, one per line, picked from the live list as "name · id". Each entry gets a "Remove <id>" action. Empty means "Any provider".
  • Model quantizations. A multi-select of the quantizations you accept: int4, int8, fp4, mxfp4, nvfp4, fp6, fp8, mxfp8, fp16, bf16, fp32 and unknown.
  • Allow fallback providers. On by default. Lets OpenRouter fall back when your chosen hosts are unavailable.

The chat-completions Reasoning effort sampler is passed through, and setting it to "none" turns reasoning off for the request. OpenRouter's own context-compression plugin is switched off on every request so Ashyo stays in charge of what the model reads. If OpenRouter rejects a request for a real model, Ashyo treats that as a context overflow and replans once.

Heads up

Preferred providers are sent as a strict allow-list, so with hosts listed under Model providers, fallback cannot route to a host outside them. See Known limitations.

OpenAI Codex

Talks to a ChatGPT subscription. Instead of an API key you log in with your OpenAI account, either in a browser or with a device code, and Ashyo keeps the resulting login in auth.json. It is Chat Completions only and the only row it adds is Model, listed from the service with display names and context windows.

Codex works differently from the others in two ways. System messages, including your system prompt and lore placed as system, are sent as instructions rather than as messages. And it honors only two samplers, Reasoning effort and Verbosity; temperature, top-p, penalties, max tokens, seed and stop strings are all dropped, see What gets sent. Reasoning summaries stream back as the reply's reasoning. When the login expires mid-session, Ashyo refreshes it and resends the request once on its own.

Accounts and credentials

Credentials are kept apart from settings in auth.json, grouped by provider as named accounts. A connection preset or a chat names an account; the account holds the key or the login. That way a preset you export never carries a secret, and several presets can share one login.

The Account row opens a list of the provider's accounts plus None and Add account…. Account names can be anything non-blank and unique; extra spaces are collapsed. An existing account row offers Rename account and Delete account, the latter warning that "Presets and chats using this account will have none." Renaming or deleting carries through to every preset, the defaults and every chat, open or saved. With no account chosen the credential row reads None with the note "No account is chosen; choose or add one to hold a credential."

API keys

For OpenRouter and OpenAI-compatible servers the credential row is API key, reading "Saved key" or "No key". Press Enter and paste the key; it is typed hidden and saved straight to the account. A blank key removes it, as the row's note says. Removing the last account of a provider removes that provider's section from the file.

Logging in to Codex

For OpenAI Codex the credential row is Login, reading "Logged in", "Not logged in" or "Logging in…". Press Enter for its actions:

  • Log in with the browser. Ashyo opens the OpenAI login page in your browser and waits for it to call back on localhost (port 1455, or 1457 when that is taken). If no browser can be opened, a notice reads "Open this URL to log in: …" so you can paste it yourself.
  • Log in with a device code. For machines without a browser, such as a remote host over SSH. A notice reads "Open https://auth.openai.com/codex/device and enter code …"; do that in any browser and Ashyo picks up the login when it completes. The offer expires after 15 minutes.
  • Cancel login while one is under way. Only one login can run at a time: "Nothing to start while another login is pending."
  • Log out. Ashyo asks OpenAI to revoke the login, then forgets it. If the revocation fails you still end up logged out: "The account is logged out regardless."

Logins refresh themselves shortly before they expire, so you should rarely see "Not logged in" again. The file holding all of this must be readable by you alone; Ashyo refuses to start otherwise, see auth.json.

Choosing a model

The Model row opens a list fetched from the service. Type to filter it by id or name, press Esc to clear the filter, and Enter to choose. The list opens on the current model and reads "Loading…" while it fetches and "No models." when the service has none. If fetching fails the reason shows as a note under the row. For providers that accept any name, your typed text is offered as "Use <text>".

You can also switch a chat's model without opening Settings: press Ctrl+P on an empty composer or type /model, see the model dock.

Context size

The context size is the number of tokens the model can read in one request, and it is the ceiling every prompt is planned against, see Context and budget. The row is unset by default. When it is unset, or when Auto-update on connect is on, Ashyo asks the provider for the model's maximum whenever a chat opens or a connection is tested, and saves the answer into the chat. Set the row by hand when you want a smaller window than the model allows, or when the provider cannot report one.

If no size is known at all when you send, the send is refused: "The provider's context window is unknown and could not be retrieved. Test the connection or set a context size."

Testing the connection

At the bottom of the tab, under Test, the Connection row shows the state of the connection and runs a test when you press Enter. The test first checks that credentials are in place, then sends "Reply with OK." asking for a single token, and finally refreshes what Ashyo knows about the service, including the context size. The row reads "Connecting" while it runs, then "Connected" in green or "Disconnected — " followed by the reason. Before any check it reads "Disconnected — not yet checked". Changing a setting clears the result and cancels a running test.

Ashyo also watches every server address on its own. When a request fails to connect, it probes the address with growing pauses (1, 2, 4, 8, 16 and then 30 seconds) until it answers again, and a generation waits for the server to come back for up to the connect timeout before failing. The reasons you will see are plain: "connection refused" with the question "Is the server running?", "cannot resolve host", "host unreachable", or "no answer" when nothing replies in time. A server that connects but then goes silent is cut off with "no data for N seconds; the request was aborted". What to do about each is in Troubleshooting.

Timeouts and proxies

Two limits are not on any screen but can be edited in the config file under backend: connect_timeout, how long to wait for a server to accept a connection (30 seconds by default), and read_timeout, how long a request may go without sending anything (300 seconds). Raise the second for slow local models that think for minutes before the first token. See the config file.

Encrypted connections are used wherever the address says https. HTTP CONNECT proxies are honored from the usual proxy environment variables; SOCKS proxies are not supported.

Connection presets

A connection you want to reuse is saved as a preset. With the tab filled in, press Tab on the Preset row for Save (into the selected preset), Save as (a new preset, named "Untitled" until you change it), Rename and Delete; the status bar confirms with "saved preset". Presets are also edited directly on the Library's Connection presets tab, where a preset shows its Route plus its provider's field groups with unset fields showing their defaults.

A preset stores only the fields its provider uses, along with its name, provider, protocol, account and context settings. Changing a preset's provider clears its account. Choosing a preset or a provider in a chat clears that chat's connection overrides, and a chat's empty connection fields fall back to the provider's defaults. Renaming a preset follows through to every chat using it; deleting one leaves those chats with no preset selected. An exported preset leaves out its account, see Ashyo item files.
