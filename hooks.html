Hooks

A hook is an executable you list in the config. Ashyo runs it before or after every tool call with the call as JSON on stdin. A hook can veto, annotate, or log. It cannot allow what policy denied, and it cannot change what runs.

Configuring

~/.config/ashyo/config.json
{
  "hooks": {
    "before": ["/home/you/.config/ashyo/hooks/guard"],
    "after":  ["/home/you/.config/ashyo/hooks/audit"]
  }
}

Paths are executables. Global hooks run first, then project hooks, each list in order. Hooks apply live like the rest of the config.

Where hooks run

  1. Policy decides the call: allow, ask, or deny. A deny stops here; no hook sees it.
  2. Before-hooks run against the exact arguments a dispatch would use. A deny from any of them resolves the call as denied and the approval pane never opens.
  3. If the decision was ask, the approval pane docks, showing what the before-hooks said.
  4. The tool runs.
  5. After-hooks run with the result attached. They can annotate; a deny at this stage has no effect.

If you edit the arguments in the approval pane, the before-hooks run again over the edited call.

What a hook receives

One JSON object on stdin:

{
  "stage":     "before",
  "tool":      "shell",
  "arguments": { "command": "go test ./..." },
  "sessionId": "6f1c2a0e-3b7d-4c1e-9a2f-0d8e5b4c7a11",
  "workerId":  "…"
}
  • stage is before or after.
  • result is present only at after: { "content", "metadata", "isError" } as the tool returned it.
  • workerId is present only when the call comes from a subagent.

What a hook may say

One JSON object on stdout. Three fields are honored; anything else is ignored and reported as an annotation naming the ignored field.

{ "deny": true, "reason": "sudo is not allowed here", "annotations": ["guard: checked"] }
  • deny vetoes the call at before. The model sees hook_denied: <reason>.
  • annotations are strings shown in the approval pane and recorded beside the unmodified result.
  • Empty stdout and {} both mean no objection.

A hook that exits non-zero, prints something that is not JSON, or prints more than one JSON value is an error, and the error ends the turn. Nothing executes. Write hooks defensively.

What is recorded

Every hook execution becomes a hook_event in the session log with its outcome: ok, deny, or error. Hook lines also appear in the transcript live and on replay.

Example

A before-hook that refuses sudo in shell commands and annotates everything else. Any language works; this one needs jq.

~/.config/ashyo/hooks/guard
#!/bin/sh
input=$(cat)
tool=$(printf '%s' "$input" | jq -r '.tool')
stage=$(printf '%s' "$input" | jq -r '.stage')

if [ "$stage" = before ] && [ "$tool" = shell ]; then
  command=$(printf '%s' "$input" | jq -r '.arguments.command // ""')
  case "$command" in
    *sudo*) printf '{"deny":true,"reason":"sudo is not allowed here"}\n'; exit 0 ;;
  esac
fi

printf '{"annotations":["guard: ok"]}\n'
$ chmod +x ~/.config/ashyo/hooks/guard

What hooks cannot do

  • Allow a call that policy denied.
  • Change the command, paths, environment, or arguments of a call.
  • Change the result the model sees.
  • Deny at after.

Hooks are a second veto and a record, deliberately. Anything that reshapes a call belongs in the model's instructions or in your rules.
