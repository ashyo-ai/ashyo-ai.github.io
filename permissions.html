Permissions

Policy is Ashyo's only sandbox. Every tool call is decided by rules you wrote, and the decision is recorded in the session. There is no other enforcement layer, on purpose: filesystem snapshots, network controls, and wrappers stay under your control outside the harness.

Rules

A rule is an object in the permissions array of either config file.

{ "action": "allow" | "ask" | "deny",
  "tool":   "<tool name>" | "*",
  "when":   [ matcher, … ] }
  • action is required.
  • tool is required. * matches every tool.
  • when is optional. When present, every matcher must match.

Matchers

A matcher points into the tool's arguments and tests the value there.

{ "pointer": "/command", "regex":    "^rm\\b" }
{ "pointer": "/path",    "glob":     "*.go" }
{ "pointer": "/path",    "contains": "/vendor/" }
{ "pointer": "/access",  "equals":   "read_only" }
  • pointer is an RFC 6901 JSON pointer into the arguments and must start with /. Argument names are on the Tools page.
  • Exactly one of equals, contains, regex, glob.
  • equals compares a JSON scalar. The other three apply to string values only; a non-string at the pointer does not match.
  • regex is Go RE2 syntax and is compiled when the config loads, so a bad pattern is a config error, not a silent non-match.
  • glob is matched against the whole value and * does not cross /. For a path deep in a tree, contains or regex is usually what you want.

Scopes and precedence

Rules come from three scopes: global from your config directory, project from .ashyo/config.json, and session for rules recorded in an older session log. A call is decided like this:

  1. Denies imposed by the execution context are checked first. See below.
  2. Then session, project, and global scope, in that order. The first scope with any matching rule decides; later scopes are not consulted.
  3. Within that scope, if several rules match, the strongest action wins: deny over ask over allow.
  4. If nothing matches anywhere, the answer is ask.

Two consequences worth knowing:

  • A wildcard ask in the same file as your allows makes every one of them ineffective, since ask beats allow within a scope. No match already means ask, so leave the wildcard out.
  • A project allow shadows a global deny for any call that matches both, because project scope is decided first. Put denies you want to survive project overrides in the project file too, or keep project allows narrow.

Interactive and uninterrupted

In the TUI, ask docks an approval pane and waits. In print mode nothing can wait, so ask is treated as allow, with the reason recorded, and the ask_user tool is withdrawn. deny is a deny in both.

The approval pane

It shows the tool, the full arguments, the rule that matched or (no rule matched), the mode and profile, and any annotations from before-hooks. The two actions are allow once and deny once. Neither creates a rule; a decision you want to keep goes in a config file and applies on the next call. Press e to edit the arguments before allowing. The log keeps the model's intended call, your edited call, and the executed call as separate fields.

What the model sees on a deny is one line: policy_denied: <tool>: <reason>. The turn continues; the model can try something else or stop.

Execution context

Some limits are not rules and cannot be overridden by rules. They are applied before the engine runs:

  • In plan mode and in a read-only subagent, shell is denied outright, and edit and write are limited to that context's writable roots: the session scratch directory for plan mode, nothing for a read-only child, its own worktree for a mutable child.
  • In print mode, ask_user does not exist.
  • File tools resolve paths against the workspace root and your home directory. Anything outside both is refused with path_outside_workspace.

Keeping the model out of the config files

The project file is applied from the first turn. Opening Ashyo in a repository is the act of trust, and nothing reviews the file first. Both config files are ordinary files under paths the model's tools can reach, and a change the model writes takes effect on the next call exactly as yours would. The harness adds no special protection; the rule set is the protection. Global denies on writes to both files close the loop:

{ "action": "deny", "tool": "edit",
  "when": [{ "pointer": "/path", "contains": "/.ashyo/config.json" }] },
{ "action": "deny", "tool": "write",
  "when": [{ "pointer": "/path", "contains": "/.ashyo/config.json" }] },
{ "action": "deny", "tool": "edit",
  "when": [{ "pointer": "/path", "contains": "/.config/ashyo/" }] },
{ "action": "deny", "tool": "write",
  "when": [{ "pointer": "/path", "contains": "/.config/ashyo/" }] }

Cover shell with a pattern on the command as well if you allow shell broadly. Remember the shadowing rule above: a project allow for edit that also matches the config path would win over these, so keep project allows on specific paths.
