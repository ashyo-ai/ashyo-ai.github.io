Config

Ashyo reads two JSON files: a global one in your config directory and an optional one in the project. Both are decoded strictly, watched while Ashyo runs, and applied live.

Files

ScopePath
Global$XDG_CONFIG_HOME/ashyo/config.json, default ~/.config/ashyo/config.json
Project<working directory>/.ashyo/config.json
Themes$XDG_CONFIG_HOME/ashyo/themes/, default ~/.config/ashyo/themes/, one <name>.json per theme

A missing file is fine and means no configuration at that scope. A file that does not parse is not: at startup Ashyo refuses to run and names the error. Unknown fields are rejected, trailing content after the JSON object is rejected, and the project file must be valid UTF-8.

Live reload

Both files are checked once a second while Ashyo runs. A saved change that parses applies at once and in full: permissions, roles, hooks, and web search, to the bound session, to every running subagent, and to the advisor. A call already decided keeps its decision; the next call anyone makes is decided under the new rules. A docked approval is answered under the rules its pane opened with. A change that does not parse changes nothing: the previous configuration stays in force and the status line shows a config: field naming the file and the error until it parses again. Deleting a file is the same as saving an empty one. A changed tui.commandCompletionLimit is in force the next time the completion dock opens, and a changed tui.inputHistoryLimit the next time you send something: entries already recorded are left where they are, and a lowered limit trims them as new entries arrive. The file of the theme in use is checked the same way, so saving it recolors the screen within a second; a theme that cannot be read leaves the colors where they are and names the theme file in the config: field. See Themes.

There is no reload command and no restart needed.

Roles

A role names a job and lists the models allowed to do it, in order of preference. The first entry is tried first; the rest are fallbacks. Each entry is an object with a model reference written as provider/model, an optional reasoningEffort passed to the provider, and an optional reasoningEfforts naming the levels that model offers. See Reasoning effort.

RoleUsed for
defaultThe main conversation. Required.
planPlan mode. Required before /plan works.
taskSubagents. Required before the agent tool can create one.
advisorA second opinion that watches the conversation and speaks to the model, and never acts. Off unless configured.
memoryMemory consolidation and the reflect tool. Off unless configured.
visionThe image tool.

A project role replaces the global role of the same name entirely, not entry by entry. --model on the command line and /model in the TUI collapse the list to that one model, so no fallback is attempted.

A role is a list of models and nothing else. Everything about the advisor except which model it runs on is set in the top-level advisor section below.

The advisor section

One optional top-level object holds every advisor setting. Keys you leave out take their defaults.

"advisor": { "enable": true, "lookBack": 8, "syncTurns": 0, "immuneTurns": 3 }

enable is the switch. Set it to false and no advisor runs, the status line's advisor field reads off, and roles.advisor stays where it is — turning the advisor off does not cost you the model list. Leaving it on with no roles.advisor configured also means no advisor, and is not an error: the role is what says which model would run. Saving either way applies at once; an advisor started by a save begins with an empty context, having seen nothing of the session so far.

syncTurns and immuneTurns are counts of main-session turns, whole and non-negative. See Waiting for the advisor and Leaving the model alone.

Unlike roles and web search, a project's advisor section replaces the global one whole rather than key by key: a project that writes the section gets its own keys and the defaults for the rest, never a global value for a key it left out.

Waiting for the advisor

The advisor answers in the background and the main model never waits for it, so on a fast conversation its notes on one turn can arrive while the next but one is already running. advisor.syncTurns is how far behind it may fall before Ashyo pauses for it, counted in your own turns: a submission, a batch of messages steered into a running turn, or a plan you approved.

With 1, a turn begins only once the advisor has started on the one before it, so its notes on your last turn are in hand for the next. With 2, it may be two turns behind before anything waits. 0, the default, never waits, which is how the advisor has always behaved.

A wait happens once, at the start of a turn, before the model is asked anything, and ends the moment the advisor picks up the updates it is behind on. The status line's advisor field reads catching up while it does, and Esc cancels the turn as it cancels any other. A wait never lasts longer than 30 seconds: past that, Ashyo writes a line into the transcript saying the advisor is still behind and the turn is going ahead, and the turn runs. The 30 seconds is fixed, so an advisor that has stopped answering costs you half a minute at worst and can never hold up the conversation.

Subagents are not your turns: a child agent's work neither counts towards the pause nor waits for it. -p mode has no advisor, so nothing waits there either. Saving a new syncTurns applies from your next turn.

Leaving the model alone after an interruption

A concern or a blocker that lands in the middle of a turn changes what the model does next. An advisor that keeps landing them turns every turn into a negotiation and the model never finishes a thought. advisor.immuneTurns is how long the main model is left alone after the advisor cuts in, counted in your own turns.

Cutting in means one of three things: a concern delivered into a turn that was already running, a blocker that cancelled the calls that turn had in flight, or a blocker that started a turn of its own. After any of them, for the rest of that turn and the next immuneTurns turns, every further concern and blocker is delivered the way a note is — with your next turn, ahead of your message, interrupting nothing and starting nothing. The turn after that may be interrupted again.

The default is 3. Because the turn a blocker starts counts as cutting in, a follow-up is followed by three turns the advisor cannot interrupt, which is what stops a chain of follow-ups. 0 switches immunity off: every concern and every blocker may cut in, and one follow-up may be followed by another, with Esc as your only stop.

A held concern or blocker keeps its kind and loses only its timing: the model is still told which it is, and the transcript shows it under its own label marked — held, so a blocker that did not interrupt is not mistaken for one Ashyo lost. Steer batches and advisor-started turns count towards the total like any other turn, and subagent work counts for nothing. Saving a new immuneTurns applies from your next turn; setting it to 0 in the middle of an immune stretch ends the immunity at the next turn rather than the one already running.

The advisor's look-back window

advisor.lookBack is how much of its own history the advisor carries into each request, counted in its own turns: one turn is one batch of session updates and the answer it gave to that batch. With 8, a request carries the last eight whole turns plus the update being answered, and everything older is dropped. Whole turns drop, so the advisor never sees an update without the answer it gave to it.

Leave it out and the advisor carries everything it has seen since the conversation was opened, which is what it has always done and what it still does unless you set the window. Setting it keeps a long session's advisor turns from growing more expensive as the session goes on; the price of a short window is that the advisor can lose track of something it was told early. 0 is a window too: the advisor sees only the update it is answering.

The advisor keeps its whole context in memory regardless, so widening the window while the conversation is open brings the earlier turns back. A negative value, or one that is not a whole number, is a configuration error like any other.

How the two files combine

  • Roles: project replaces global, per role.
  • Advisor: project replaces global as a whole section, not key by key.
  • Permissions: both sets are kept; project rules are consulted before global ones. See scopes.
  • Hooks: appended, global first, then project, and run in that order.
  • Web search: merged field by field; a project value wins where set.

Reasoning effort

Reasoning effort is model-specific: every model offers an ordered set of levels drawn from none, minimal, low, medium, high, xhigh, max. Ashyo ships the sets for the models it knows, read from each provider's documentation. A model it does not know offers low, medium, high, and takes whatever reasoningEffort you write for it, because only its provider knows better.

reasoningEfforts on an entry declares that model's set and replaces whatever Ashyo ships for it — for a model newer than your Ashyo, or one whose shipped set is wrong. The list must be drawn from the scale above, in ascending order. An empty list declares a model with no reasoning control at all: it is sent no effort, shows no thinking field, and /thinking <level> says so.

{
  "roles": {
    "default": [
      { "model": "openai-codex/gpt-5.2-codex", "reasoningEffort": "xhigh" },
      { "model": "openrouter/house-model", "reasoningEfforts": ["none", "low", "high"] },
      { "model": "openrouter/no-thinking", "reasoningEfforts": [] }
    ]
  }
}

A reasoningEffort outside the model's known set is a configuration error naming the field, as is a reasoningEfforts that names a word off the scale or lists levels out of order.

What a request carries is the level chosen with /thinking mapped into the set of whichever model runs, fallbacks included; reasoningEffort here is what runs when nothing has been chosen in session.

Complete example

~/.config/ashyo/config.json
{
  "roles": {
    "default": [
      { "model": "openai-codex/gpt-5.6-luna", "reasoningEffort": "medium" },
      { "model": "openrouter/~z-ai/glm-flash-latest" }
    ],
    "plan":    [{ "model": "openai-codex/gpt-5.6-luna", "reasoningEffort": "high" }],
    "task":    [{ "model": "openrouter/~z-ai/glm-flash-latest" }],
    "advisor": [{ "model": "openrouter/~z-ai/glm-flash-latest" }],
    "memory":  [{ "model": "openrouter/~z-ai/glm-flash-latest" }]
  },
  "advisor": { "lookBack": 8 },
  "permissions": [
    { "action": "allow", "tool": "read" },
    { "action": "allow", "tool": "grep" },
    { "action": "allow", "tool": "glob" },
    { "action": "allow", "tool": "recall" },
    { "action": "deny",  "tool": "shell",
      "when": [{ "pointer": "/command", "regex": "^rm\\b" }] },
    { "action": "allow", "tool": "edit",
      "when": [{ "pointer": "/path", "glob": "*.go" }] }
  ],
  "hooks": {
    "before": ["/home/you/.config/ashyo/hooks/guard"],
    "after":  ["/home/you/.config/ashyo/hooks/audit"]
  },
  "memory": {
    "dbPath": "/home/you/.local/share/ashyo/memories.db"
  },
  "webSearch": { "backend": "auto", "maxResults": 5 },
  "tui": {
    "commandCompletionLimit": 10,
    "inputHistoryLimit": 1000,
    "theme": { "dark": "graphite", "light": "paper" }
  }
}

Anything not matched by a rule asks. Do not add a wildcard ask to make that explicit: within one file the strongest matching action wins, so a wildcard ask would override every allow beside it.

Project example

.ashyo/config.json
{
  "roles": {
    "default": [{ "model": "openai-codex/gpt-5.6-luna", "reasoningEffort": "high" }]
  },
  "permissions": [
    { "action": "allow", "tool": "shell",
      "when": [{ "pointer": "/command", "regex": "^go (build|test|vet)\\b" }] }
  ]
}

Opening Ashyo in a repository is the act of trust: the project file is applied from the first turn, and nothing reviews it first. Since the model can edit this file with its own tools, a deny rule on writes to it is the way to keep the model out of its own permissions. See Permissions.
